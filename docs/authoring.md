# Writing a Reforge mod

## Layout

```
MyMod/
  MyMod.mod
  reforge.json                      # the list of replaced files (edit this, or use the CLI)
  bin/reforge.dll                   # copied by `reforge build`/`sync`
  bin/REFORGE_NOTICES.txt           # licence notices; must ship with the DLL
  payload/…                         # your edited files
  scripts/mods/MyMod/MyMod.lua
  scripts/mods/MyMod/reforge.lua            # copied by `reforge build`/`sync`
  scripts/mods/MyMod/reforge_manifest.lua   # generated by `reforge build`
```

## reforge.json

```json
{
  "schema": 1,
  "redirects": [
    { "stock": "bundle/98bb14b1d247a0c8", "file": "payload/98bb14b1d247a0c8", "sha256": "9086f5…" },
    { "stock": "bundle/data/mymod/extra", "file": "payload/extra.bin", "virtual": true, "priority": 0, "contract": "mymod-rgb-v1" }
  ],
  "virtual_dirs": [
    { "stock": "bundle/data/mymod/materials", "dir": "payload/materials" }
  ]
}
```

- `sha256` pins the stock file. After a game update the file stays stock
  until you rebuild. This stops an old payload from being served against new
  game data.
- `virtual` entries serve paths that do not exist in the game. Use them for
  new resources that a replaced bundle refers to.
- `virtual_dirs` expands every file in `dir`. File names must be lowercase.
- `priority` decides between mods that replace the same file. Higher wins, and
  on a tie the first to register wins. `contract` is a free-form string: two
  mods with the same contract report `compatible` rather than `displaced`.

## Lua API

```lua
local reforge = mod:io_dofile("MyMod/scripts/mods/MyMod/reforge")
local handles = reforge.register_manifest(mod, "MyMod/scripts/mods/MyMod/reforge_manifest")
-- or: local h = reforge.register(mod, { stock = "bundle/…", file = "payload/…", sha256 = "…" })

mod.on_all_mods_loaded = function()
    reforge.commit()                      -- loads the DLL once for all mods
    for _, h in ipairs(handles) do
        local state = reforge.state(h)    -- see README "File states"
        if not reforge.served(state) then
            mod:info("%s: %s %s", h.stock, state, reforge.reason(h) or "")
        end
    end
end
```

| Function | Purpose |
|---|---|
| `reforge.register(mod, spec)` | Registers one file. Registering the same stock again from the same mod updates it, which is safe on hot reload. |
| `reforge.register_manifest(mod, path_or_table)` | Registers every entry of a schema 1 manifest. |
| `reforge.commit()` | Loads the DLL and applies registrations. Later registrations apply immediately. |
| `reforge.state(h)`, `reforge.served(state)`, `reforge.reason(h)`, `reforge.winner(h)` | Per-file result. |
| `reforge.clear(mod)` | Drops every registration from `mod`, for example in `on_unload`. |
| `reforge.set_enabled(bool)` | Toggles serving for files opened afterwards. |
| `reforge.version()` | Returns the library version and the DLL version. |
| `reforge.status()` | Returns a table with the same data as `/reforge`. |

## Several mods, one DLL

Each mod ships its own `reforge.lua` and `bin/reforge.dll`. The first
library to load stores its state in `_G.__reforge_instance`, and every later
copy uses that shared state. At commit, the DLL is loaded once. The candidates
are tried in this order:

1. An already loaded `reforge.dll`.
2. The copies shipped by mods with the newest library version.
3. The remaining copies.

A newer library version takes over only before commit. Otherwise it reports
that a restart is needed.

## Editing shaders and materials

Replacement bundles (`bundle/<16 hex>` files, format 8) must be
Oodle-compressed like the stock ones. The game's DirectStorage reader crashes
on chunks stored uncompressed, even though its regular reader accepts them.

Darktide also reads some bundles before any mod runs, for example the weapon
effects of the character shown in the menu. When it loads them later, it
uses the stock chunk table it already has. For those bundles the replacement
must match the stock layout exactly: same file size, chunk count and chunk
sizes. `reforge pack <mod> --game <folder>` does this for edits that keep the
stock record list. It compresses each chunk with the game's own
`oo2core_9_win64.dll` and zero-pads it to the stock chunk size. `reforge
build --game` warns about any bundle that does not match.

### Adding new resources (host packages)

New resources, such as extra particle variants, do not fit an early-loaded
bundle. Use a host package instead:

1. Pick an existing package that the game never loads on its own. A debug
   effect such as `content/fx/particles/debug/flame_thrower_test` works; the
   bundle file name is the murmur64 of the package name.
2. Replace its bundle with the stock contents plus your new records, and mark
   the entry `"late_load": true` in `reforge.json`.
3. After `reforge.commit()`, load any stock packages your records depend on
   (for example textures), then load the host with `mod:load_package(name,
   nil, true)`. Otherwise the new records bind to default resources.
4. Use a new resource only when `Application.can_get_resource(type, name)`
   is true, and fall back to the stock one otherwise.

RainbowFlame uses this for its colour presets.

Resource streams under `bundle/data/` are not chunk-compressed and need no
packing.

Reforge only delivers files. Producing a correct edited bundle, material or
shader program is up to the mod. Keep your extraction and rebuild scripts, and
the game build they were made against, in your mod's development folder. Do
not put them in `payload/`. `reforge verify --game …` tells you when a game
update means you need to regenerate.
